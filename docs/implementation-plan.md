# Tranfr — Implementation Plan (research-grounded)

## Context

The original brief asked for Tranfr to be built as a *composition of two existing, deployed CKB scripts* — the RFC 0039 cheque lock and a "ckb-proxy-locks/time-lock" — with zero custom lock script. Direct research (RFC text, the cheque lock's actual Rust source repo, GitHub org/repo/code search across `nervosnetwork` and the wider ecosystem) shows that premise doesn't hold:

- **Cheque lock (RFC 0039)** is real and deployed on both mainnet and testnet ([duanyytop/ckb-cheque-script](https://github.com/duanyytop/ckb-cheque-script)), but its roles are inverted from what Tranfr needs (receiver claims *anytime*, sender withdraws only *after* a wait) and its timeout is a **hardcoded 6 epochs (~24h)** baked into the deployed script — not a per-cell, configurable parameter. It cannot deliver an adjustable, renewable ~90-day window.
- **"ckb-proxy-locks/time-lock"** does not exist — confirmed via GitHub repo search, code search, and a full listing of the `nervosnetwork` org's repos. Nothing under that name, and no equivalent canonical, deployed, general-purpose timelock script was found. The closest real thing (Omnilock's RFC 0042 time-lock flag) is a single-owner global gate, not a two-role primitive, and pairing it with cheque would require unverified assumptions about cheque's internal auth-matching that aren't worth building a product on.

Given this, the decision was made to build **one small custom lock script (~60–100 lines)** — owner unlocks anytime, recipient unlocks only once an embedded deadline has passed — instead of composing borrowed scripts. This is architecturally simpler than the project's own earlier README draft (which had a multi-phase `BEGIN_OWNER_OP`/`PENDING_OWNER_OP` state machine to solve an upper-bound race condition). That race doesn't reappear here: the owner path is *unconditional* (no time check at all), and the recipient path only needs a *lower-bound* `since` check — exactly what CKB's `since` mechanism was designed to enforce safely, checked against real chain tip at inclusion time, not at signing time.

The plan below reuses confirmed, load-bearing precedent rather than re-deriving it:
- The lower-bound-check pattern itself mirrors `ckb-system-scripts`' own `check_since` helper and Omnilock's RFC 0042 time-lock flag (`since` field embedded in args, enforced against the input's actual `since` value regardless of signer) — both real, running code, not invented here.
- `since`'s exact bit layout (RFC 0017): bit 63 = relative/absolute flag, bits 61–62 = metric (00 block number, 01 epoch-with-fraction, 10 timestamp-median, 11 invalid), low 56 bits = value; epoch-with-fraction packs `(index:16, length:16, number:24)`. Comparing two epoch-fraction values with different denominators needs cross-multiplication, not naive comparison — a documented footgun the plan calls out explicitly rather than leaving to chance.
- Toolchain: `ckb-std` (Rust script runtime) + `ckb-testtool` (current standard test harness) on the contract side; **CCC** (`ckb-devrel/ccc`) as the TypeScript SDK base — confirmed via current Nervos docs to be the presently recommended CKB JS/TS SDK, with Lumos explicitly no longer recommended for new projects.

Open items the plan surfaces rather than guesses past:
- Whether `since`'s timestamp metric is seconds or milliseconds is not confirmed from RFC text alone — the plan uses the **epoch-fraction** metric specifically to sidestep this ambiguity (epoch-fraction is unambiguous and consensus-native), and defers timestamp-unit confirmation to source inspection only if epoch-fraction proves unsuitable for UX.
- Capsule's current maintenance status is unverified — the plan checks it before committing, with `ckb-script-templates` + raw `ckb-std` as the fallback scaffold.

## Repository state

Currently just `README.md` (a prior design doc for a different, more complex custom-script approach) — no contracts, SDK, or demo code exists yet. This plan starts from a clean slate and will rewrite the README's mechanism section (step 21) to match what's actually being built.

## 21-Step Plan

1. **Freeze the on-chain data layout** in `/docs/spec.md`: args = `owner_lock_hash (32B, blake2b256)` + `recipient_lock_hash (32B)` + `deadline_since (8B, RFC 0017 epoch-fraction, absolute)`; `witness.lock` = `mode (1B: 0=OWNER,1=RECIPIENT)` + `signature (65B, secp256k1 recoverable)`.
2. **Port the fraction-safe since-comparison algorithm** (cross-multiply `(index/length)` pairs rather than naive float/ratio comparison) from `ckb-system-scripts`' `check_since` (`common.h`) — write it once as a reviewed, tested function; do not reimplement it separately in Rust and TypeScript from memory.
3. **Confirm real epoch length** for sizing "90 days": query `get_current_epoch` / recent epoch history on testnet to get the live average epoch length (nominally ~4h, i.e. ~6/day, ~540/90 days) rather than hardcoding an assumed constant, since CKB's difficulty adjustment can shift it.
4. **Scaffold the Rust script project**: check whether Capsule is still maintained (recent commits/releases); if stale, scaffold via `cargo generate` from `ckb-script-templates` + `ckb-std` directly instead.
5. **Implement args/witness parsing** with `ckb-std` syscalls (`load_script`, `load_witness_args`) — fixed-width hand-rolled parsing, no molecule schema needed given the small fixed layout from step 1.
6. **Implement the OWNER path**: verify the recoverable secp256k1 signature against `owner_lock_hash`, unconditionally — no since check, ever, on this branch.
7. **Implement the RECIPIENT path**: verify the signature against `recipient_lock_hash`, then load this input's actual `since` (`load_input_since` via `ckb-std`), assert its metric flag is absolute + epoch-fraction (matching args), and assert its value ≥ `deadline_since` using the step-2 comparison.
8. **Add defensive rejects**: unknown mode byte; relative-flagged `since` on the recipient path (would anchor to cell commitment time, not real time — defeats the guarantee); metric mismatch; malformed args length.
9. **Write the adversarial test suite** with `ckb-testtool`: owner spends before/after deadline (both succeed); recipient claims before deadline (fails); recipient claims at exact boundary (only succeeds when truly ≥, covering `I/L` edge cases); recipient supplies relative `since` (fails); mode byte reused to steal the other path's signature (fails — signature won't verify against the wrong hash); malformed/short args or witness (fails cleanly, no panic).
10. **Deploy the compiled binary to testnet** as a `type`-hashed cell dep; confirm current official testnet identity/genesis before deploying (network names have changed before); record code_hash/tx_hash/index in `/docs/deployment.md`.
11. **Make the deployment independently reproducible**: publish the exact deploy steps/script (`ckb-cli` or `offckb`) so a third party can rebuild the binary and re-derive the same code_hash — no "trust me" deployment info.
12. **Scaffold the TypeScript SDK** on top of **CCC** (`ckb-devrel/ccc`) rather than hand-rolling RPC/transaction/cell plumbing.
13. **Implement args/witness codecs**: `encodeArgs`/`decodeArgs`, `encodeWitnessLock`/`decodeWitnessLock` matching step 1's byte layout exactly; add cross-language golden-vector tests so a Rust-side encoding and TS-side encoding of the same logical values are byte-identical (catches drift immediately, not just "should work in theory").
14. **Implement `isRecoveryEligible(deadlineSince)`**: fetch current tip epoch via CCC's RPC client, compare using the *same* step-2 comparison function (single source of truth, not a third reimplementation).
15. **Implement `getTranfrStatus(cellOutPoint)`**: fetch the live cell, decode lock args, combine with `isRecoveryEligible` to return `{owner, recipient, deadline, claimable, epochsRemaining}`.
16. **Implement `createTranfr({ownerLock, recipientLock, capacity, durationEpochs})`**: build a tx with one output using the deployed script (code_hash/hash_type from step 10) and args encoding `deadlineSince = currentEpoch + durationEpochs` (default ≈ value from step 3).
17. **Implement `renewTranfr({cell, newDurationEpochs, newRecipientLock?})`**: owner-mode spend of the existing cell into a new output with a freshly computed deadline (and optionally a new recipient) — this *is* both "heartbeat" and "policy update," since the owner path is unconditional and there's no separate on-chain renewal transaction type needed.
18. **Implement `buildOwnerReclaim` and `buildRecoveryClaim`**: both spend the Tranfr cell to an arbitrary destination lock. Reclaim sets witness mode=OWNER with no since requirement. Claim sets witness mode=RECIPIENT and sets the input's `since` ≥ the cell's embedded deadline; `buildRecoveryClaim` calls `isRecoveryEligible` first and throws client-side rather than constructing a transaction consensus would reject anyway.
19. **Build the testnet demo web UI** (`/demo`) wired to the SDK and a CCC-supported wallet connector (confirm which connectors CCC currently ships before committing the UI flow to one) covering: create, renew, live status/expiry countdown, and recover-as-recipient — exercised against the real testnet deployment from step 10, not a mock.
20. **Write `/docs/spec.md` (finalized) and `/docs/security-model.md`**: why the owner path is unconditional, why the recipient path must reject relative-flagged/mismatched-metric `since` values, exact boundary semantics at equality, and explicit non-goals (single recipient only, no off-chain notification, not audited) — matching the honesty of the current README's "Known limitations" section.
21. **Rewrite the root `README.md`**: replace the superseded `BEGIN_OWNER_OP`/`PENDING_OWNER_OP` state-machine description with this finalized single-script mechanism, correct the References section (cite RFC 0017 accurately; drop RFC 0022/CoBuild references that no longer apply), and link the real testnet code_hash/tx_hash from steps 10–11.

## Progress

- **Step 1 — done.** On-chain data layout frozen in `docs/spec.md`.
- **Step 2 — done.** Fraction-safe `since` comparison ported from verified `ckb-system-scripts` source and independently tested in both languages: `reference/since-cmp-rs` (Rust, `cargo test`, 11/11 passing, `no_std`-clean) and `reference/since-cmp-ts` (TypeScript, `node --test`, 11/11 passing). Testing surfaced a real gap not visible from the RFC text alone — the raw ported comparison doesn't normalize a degenerate `(index=0,length=0)` fraction, which would otherwise let a recipient claim early — now closed at the Tranfr policy layer (`recipient_path_eligible`/`recipientPathEligible`) and documented in `reference/README.md` and `docs/spec.md` §5/§7.
- **Step 3 — done.** Live-queried both networks' public RPCs (`docs/epoch-length.md`) instead of assuming the nominal ~4h epoch figure: 40 real epoch transitions each gave 540 epochs/90 days on testnet, 539 on mainnet (within ~0.2% of each other). Recommendation recorded for later SDK steps: hardcode 540 as the default `durationEpochs`, but compute display-only "days remaining" from the *live* epoch length, not from that constant, since epoch wall-clock length is consensus-adjusted and drifts with network conditions rather than being fixed.

## Verification

- Steps 4–9 are verified locally: `cargo test` under `ckb-testtool` must pass the full adversarial suite in step 9 before any testnet deployment.
- Steps 10–11 are verified by having a second machine/session rebuild the script from source and confirm an identical code_hash before trusting the deployment.
- Steps 12–18 are verified via the golden-vector tests (step 13) plus integration tests that build real transactions with the SDK and dry-run them against the testnet RPC (`send_transaction` with `outputs_validator: "passthrough"` or a local `ckb-debugger` run) — not just unit tests against mocked RPC responses.
- Step 19 is verified by manually walking the golden path (create → renew → wait/observe countdown → recover) against the live testnet deployment, plus the edge case of an owner reclaiming after the deadline has technically passed (must still succeed).
